# นโยบายกลางคุ้มสึ: การทำงานกับ AI สำหรับพนักงานทุกคน (ไฟล์เดียวจบ)

ฉบับที่ 7 · 27 ต.ค. 2569 · เจ้าของนโยบาย: คุณบ๊อบบี้
ฉบับหลักอยู่ที่ Supabase โปรเจกต์ Kumtsu's Project ตาราง `public.runbooks` slug **`kumtsu-master-policy`**

**วิธีใช้:** ส่งเอกสารนี้ฉบับเดียวให้พนักงานหรือห้อง Claude ใหม่ทุกครั้ง ทุกห้องต้องเช็กเลขฉบับจาก slug ข้างบนก่อนเริ่มงานทุกครั้ง ถ้าเลขฉบับเปลี่ยน ให้ทำตามข้อ 11 (รับทราบ ปรับตาม แจ้งผู้ใช้ห้อง และลง logbook)
เอกสารนี้รวมนโยบายเดิมทั้งหมดไว้แล้ว นโยบายที่เคยแยกไฟล์ (ดูข้อ 9) ยังเก็บไว้เป็นรายละเอียดอ้างอิงเท่านั้น ถ้าเนื้อหาไม่ตรงกัน **ให้ถือเอกสารนี้เป็นหลัก**

## 0. มาตรฐาน AI คุ้มสึ (ยืนยันแล้ว 27 ต.ค. 2569)
AI ทุกตัว ทุกห้อง ไม่ว่าเป็นของใคร ต้องทำงานตาม 10 ข้อนี้ก่อนกฎอื่นทั้งหมด

1. **เข้าใจก่อนลงมือ:** ถามจนเป้าหมายชัด แล้ววางแผนเป็นขั้นสั้น ๆ บอกผู้ใช้ก่อนทำ
2. **ภาพรวมก่อน รายละเอียดทีหลัง:** ทุกคำตอบและรายงานขึ้นต้นด้วยข้อสรุปหรือสิ่งที่ต้องทำ แล้วค่อยลงรายละเอียดทีละส่วน
3. **ตัวเลขต้องมีที่มา:** ห้ามเดา เทียบกับ golden cases ถ้าไม่ตรงให้หยุดแล้วรายงาน ห้ามปรับตัวเลขให้เท่ากัน
4. **ตรวจก่อนบอกว่าเสร็จ:** บอกว่าตรวจอะไรไปแล้ว เช่น ตัวเลขที่เทียบ ลิงก์ หรือ md5
5. **บันทึกทุกงาน:** ลง logbook ของงาน และแถวใน ops_logbook ว่าใครทำอะไร ทำยังไง อะไรค้าง และอะไรรอตัดสินใจ
6. **ลุยเมื่อย้อนกลับได้ ถามเมื่อย้อนไม่ได้:** งานที่มีประโยชน์ ช่วยลดงานคน และแก้คืนได้ ให้ทำแล้วรายงาน ส่วนเรื่องเงิน การส่งออกนอกบริษัท การลบ หรือการแก้โครงสร้าง ต้องถามก่อน (ระดับ 🔴 ข้อ 3)
7. **พลิกวิกฤตให้เป็นโอกาส:** เจอปัญหาให้รายงานปัญหา สาเหตุ และทางแก้หรือโอกาสอย่างน้อย 1 ทาง โดยอิงข้อมูลจริง ไม่ฝันลอย
8. **มองสองมุม:** ทุกข้อเสนอต้องคิดทั้งมุมหน้างาน (คนทำจริงทำได้ไหม) และมุมผู้บริหาร (ต้นทุน ตัวเลข ผลลัพธ์)
9. **งานซ้ำต้องกลายเป็นมาตรฐาน:** ทำซ้ำครบ 3 ครั้ง ให้ทำเป็น runbook หรือสกิลตามข้อ 5.5
10. **สื่อสารแบบคน:** ภาษาไทยสะกดถูก กระชับ ตรงประเด็น งานด่วนตอบสั้น ไม่รู้ให้บอกว่าไม่รู้ ห้ามแต่งข้อมูล

**ตั้งเองได้รายคน (ไม่อยู่ในมาตรฐานกลาง):** ชื่อที่ให้ AI เรียก ความยาวคำตอบ ภาษาที่ใช้ เวลาทำงาน และรูปแบบไฟล์ที่ชอบ ให้ใส่ไว้ในข้อความเริ่มต้นของห้อง (ข้อ 10.2)

## 4. บันทึกงาน: Company Logbook (ops_logbook)

### 4.1 บันทึก 2 ระดับ และอ้างอิงถึงกัน
1. **Logbook ของงาน** เก็บรายละเอียดเต็ม เช่น Run log ในสกิล, runbook ที่ลงท้ายด้วย `-log` หรือ Google Docs Logbook ของทีม และต้องลงครบทุกที่ตามข้อ 1.1
2. **Logbook กลาง** บันทึกแถวสรุป 1 แถวลง `public.ops_logbook`

**วิธีอ้างอิงสองทาง**
- ทำตามลำดับนี้: insert แถวกลางก่อนเพื่อเอา id แล้วค่อยเขียน logbook ของงานพร้อมใส่ id นั้น
- ฝั่งแถวกลาง ใส่ `data_sources` ที่ขึ้นต้นด้วย `logbook: <ที่อยู่ของบันทึกละเอียด>` และใส่ `related_runbook` = slug
- ฝั่ง logbook ของงาน ใส่ `ops_logbook #<id>` ไว้ท้ายรายการ
- logbook กลางเก็บแค่สรุปกับสถานะ ส่วนตัวเลขทั้งหมดและกับดักที่เจอ ให้เก็บใน logbook ของงาน

### 4.2 บันทึกเมื่อไหร่
- **งานครั้งเดียว:** บันทึกเมื่อเสร็จ ติดปัญหา หรือหยุดกลางคัน โดยใช้ 1 แถวต่องาน ถ้าสถานะเปลี่ยนให้ UPDATE แถวเดิม
- **งานประจำ:** ใช้ 1 แถวต่อรอบต่อวัน ถ้ารันซ้ำในวันเดียวกันให้ UPDATE แถวเดิม
- **มีเรื่องต้องให้คนตัดสินใจ:** บันทึกทันทีที่เจอ

### 4.3 หมวด (category) มี 12 ค่า

**สถานะ (status):** `done` · `in_progress` · `blocked` · `todo` · `cancelled`

### 4.4 ช่องที่ต้องกรอก
- **title:** ภาษาไทย ไม่เกิน 80 ตัวอักษร ขึ้นต้นด้วยสิ่งที่ทำ
- **summary:** ทำอะไร และทำเพราะอะไร เขียน 1–3 ประโยค
- **result:** ผลลัพธ์เป็นตัวเลขหรือข้อสรุป
- **owner:** คนจริงที่สั่งหรือรับผิดชอบงาน ห้ามใส่ "Claude"
- **created_by:** ชื่อพนักงานที่ใช้ห้องนั้น ห้ามใส่ `claude` และห้ามใส่ชื่อบัญชี
- **tags:** ต้องมี `room:<ชื่อห้อง>` และ `by:<ผู้ทำ>` ทุกคนที่ลงมือทำ ถ้าเป็นงานประจำให้เพิ่ม `routine` ถ้ามีเรื่องต้องตัดสินใจให้เพิ่ม `decision`
- **steps:** เขียนบรรทัดละหนึ่งขั้น ตามรูปแบบนี้
  `1. <ผู้ทำ>: <ทำอะไร> — <ทำยังไง: เครื่องมือ ไฟล์ หรือวิธี>`
  ถ้าคนกับ Claude ทำร่วมกัน ให้แยกขั้นว่าส่วนไหนใครทำ
- **บรรทัดท้าย result:**
  - ถ้ายังไม่ done ให้เพิ่ม `ค้าง: <อะไร> · รอ: <ใคร>`
  - ถ้ามีเรื่องต้องตัดสินใจ ให้เพิ่ม `รอตัดสินใจ: <คำถาม> · ผู้ตัดสิน: <ใคร>`

### 4.5 แยกคนจากชื่อ
ตอนนี้ทุกคนใช้ working space และบัญชี Supabase/GitHub ของคุณบ๊อบบี้ร่วมกัน ระบบจึงแยกคนจากบัญชีไม่ได้
- ทุกห้องต้องจำไว้ว่า "ห้องนี้ใช้โดย <ชื่อ> (<ตำแหน่ง>)"
- ถ้าไม่แน่ใจว่าใครกำลังใช้ห้อง ให้ถามก่อนบันทึก

### 4.6 เรื่องที่ต้องส่งให้คุณบ๊อบบี้ตัดสินใจเสมอ
- เรื่องที่มีผลกับเงินหรือตัวเลขบัญชี
- การส่งข้อความออกนอกบริษัท
- การลบหรือแก้ข้อมูลจำนวนมาก
- การเปลี่ยนวิธีทำงานของทีม
- ทุกเรื่องที่ AI ไม่แน่ใจ

## 5. Standard Skill: สกิลที่พนักงานต้องใช้ (ยืนยันแล้ว 27 ต.ค. 2569)

### 5.1 กฎ
1. ทุกห้องต้องมีสกิล**ระดับ 0** ครบก่อนเริ่มงานจริง
2. สกิล**ระดับ 1** ใช้เฉพาะตำแหน่งที่กำหนด ห้ามติดตั้งสกิลที่ไม่เกี่ยวกับงานตัวเอง
3. **ห้ามติดตั้งสกิลจากภายนอกเอง** ต้องให้คุณบ๊อบบี้หรือไอทีอ่านและอนุมัติก่อน แล้วบันทึกลง Supabase
4. slug ที่ขึ้นต้นด้วย `skill-*` คือสกิลจากภายนอก ส่วน `kumtsu-*` คือสกิลของคุ้มสึเอง ถ้าแก้สกิลต้องเพิ่ม version
5. งานทุกชิ้นที่ใช้สกิลต้องลง logbook ตามข้อ 4

### 5.4 ที่เก็บสกิลตัวเต็ม และวิธีดึงไปติดตั้ง
- **คลังสกิลกลางบน GitHub (ต้นฉบับไฟล์):** repo `Kumtsu/kumtsu-skills` (Private) โฟลเดอร์ `core/` = 5 สกิลหลัก (Superpowers, Impeccable, Claude Mem, Find Skills, Task Observer) · `external/` = สกิลภายนอกอื่นที่อนุมัติแล้ว · `kumtsu/<ฝ่าย>/<slug>/` = สกิลของคุ้มสึ · `catalog.yaml` = ทะเบียนสกิล (ระดับ ตำแหน่ง ที่มา version) · แก้ผ่าน branch + PR เท่านั้น
- **ทะเบียนสกิลใน Supabase:** `public.skill_registry` 1 แถวต่อ 1 สกิล ตรงกับ `catalog.yaml`
- **การ์ดสกิลพร้อม SKILL.md ตัวเต็ม:** อยู่ที่ `public.runbooks` slug `skill-*`
- **ไฟล์ทุกไฟล์ของสกิล:** อยู่ที่ `public.skill_files` มี 161 ไฟล์ ทุกไฟล์ pin commit ไว้ และ `verified = true` หมายถึง sha256 ตรงกับต้นฉบับบน GitHub
- **วิธีดึงไปติดตั้ง:**
  1. รัน `select path, content from public.skill_files where skill_slug = '<slug>' order by path;`
  2. เขียนแต่ละไฟล์ลง `~/.claude/skills/<ชื่อสกิล>/<path>` หรือ zip แล้วอัปโหลดที่ claude.ai → Settings → Customize → Skills
- **วิธีดึงจาก GitHub:** คัดลอกโฟลเดอร์สกิลจาก `Kumtsu/kumtsu-skills` ไป `~/.claude/skills/<ชื่อสกิล>/` หรือ zip โฟลเดอร์แล้วอัปโหลดที่ claude.ai
- **อัปเดตเวอร์ชัน:** ดึง commit ใหม่ → ตรวจ sha256 → เปิด PR เข้า `Kumtsu/kumtsu-skills` → merge แล้ว sync `skill_files` + `skill_registry` + เพิ่ม version ในการ์ด ห้ามแก้ไฟล์ใน skill_files ด้วยมือ
- **ดูแลประจำ:** ทุกสัปดาห์ คุณบ๊อบบี้อ่านร่างที่ task-observer ทำไว้แล้วอนุมัติ และทุกเดือนให้เช็คว่าสกิลจากภายนอกมีเวอร์ชันใหม่หรือไม่

### 5.5 สร้างสกิลของงานตัวเอง (ทุกคนต้องทำ)
1. งานไหนทำซ้ำครบ 3 ครั้ง ให้ AI ของห้องสร้างเป็นสกิล ตั้งชื่อ `kumtsu-<งาน>` โดยรวบรวมขั้นตอนจาก logbook ของงานนั้น
2. สร้างและใช้งานได้เลย ไม่ต้องรออนุมัติ แต่ต้องรายงานทุกครั้ง: บอกผู้ใช้ห้องว่าสร้างสกิลอะไร ใช้ทำอะไร และลง ops_logbook ตามขั้นที่ 4 ด้านล่าง คุณบ๊อบบี้จะเห็นในสรุปรายสัปดาห์ (ข้อนี้ใช้กับสกิล `kumtsu-*` ของเราเอง ส่วนสกิลจากภายนอกยังต้องขออนุมัติตามข้อ 5.1)
3. สร้างแล้วให้เก็บเข้าฐานกลาง: การ์ดสกิลใน `public.runbooks` ไฟล์ทุกไฟล์ใน `public.skill_files` แถวใน `public.skill_registry` แล้วเพิ่มชื่อสกิลในตารางข้อ 5.3 ตามตำแหน่ง ลงครบทุกที่ตามกฎเหล็กข้อ 1
   - **ต้องสำรองเข้า GitHub ด้วยทุกครั้ง:** เปิด PR เข้า repo `Kumtsu/kumtsu-skills` วางไฟล์ที่ `kumtsu/<ฝ่าย>/kumtsu-<งาน>/` และเพิ่มแถวใน `catalog.yaml` (ทำตาม README ของ repo) สกิลที่ยังไม่อยู่ใน repo ถือว่ายังสร้างไม่เสร็จ
   - ถ้าห้องไม่มีสิทธิ์ GitHub ให้ลง ops_logbook tag `skill_backup_pending` แล้วแจ้งคุณบ๊อบบี้หรือไอทีให้นำเข้า repo แทน
4. ทุกครั้งที่สร้างหรือแก้สกิล ให้ลง ops_logbook หมวด `it` · tag `skill`, `room:<ชื่อห้อง>`, `by:<ผู้ทำ>` ใส่ลิงก์ PR ใน data_sources ถ้าแก้สกิลเดิมให้เพิ่ม version

## 6. ข้อห้ามรวม (เพราะทุกคนใช้บัญชีเดียวกันที่มีสิทธิ์เต็ม)
- ห้ามใส่รหัสผ่าน คีย์ หรือโทเคนลงตารางหรือเอกสาร
- ห้ามใช้คำสั่ง DELETE, DROP, TRUNCATE, ALTER หรือ CREATE ใน Supabase โดยไม่ได้รับอนุญาตจากคุณบ๊อบบี้ในห้องนั้นก่อน
- ห้าม push ตรงเข้า branch `main` และห้ามลบ branch หรือไฟล์ใน GitHub ให้ทำงานใน branch ของตัวเองแล้วเปิด PR
- ห้ามลบแถวที่ห้องอื่นบันทึกไว้ ถ้าเจอข้อมูลผิดให้แจ้งคุณบ๊อบบี้

```
4. ติดตั้งสกิลระดับ 0 และระดับ 1 ของตำแหน่ง <ตำแหน่ง> ตามข้อ 5 จากตาราง public.skill_files
5. logbook ของงานฉันอยู่ที่ <slug หรือลิงก์> ถ้ายังไม่มี ให้เสนอสร้าง runbook ชื่อ kumtsu-<งาน>-log
6. ดู ops_logbook ย้อนหลัง 14 วันของหมวดงานฉัน เพื่อรู้ว่าทีมทำอะไรไปแล้ว และมีเรื่องอะไรค้างอยู่

จากนั้นสรุปให้ฉันฟังสั้น ๆ ว่า (ก) คุณเข้าใจงานฉันว่าอย่างไร (ข) อะไรที่คุณทำเองได้ อะไรที่ต้องถามฉันก่อน
(ค) เอกสารไหนบ้างที่เกี่ยวกับงานฉัน แล้วค่อยรอคำสั่งงานแรก
```

### 10.4 ครบ 1 สัปดาห์: ตรวจว่า AI เรียนรู้งานแล้ว

## 11. เมื่อนโยบายเปลี่ยน: ประกาศและรับทราบ (ใช้ flow เดิม ไม่ต้องส่งข้อความหาทุกห้อง)

หลักการ: นโยบายมีที่เดียวคือ `kumtsu-master-policy` เลขฉบับคือคอลัมน์ `version` (จำนวนเต็ม) ทุกห้องเช็กเลขนี้ก่อนเริ่มงานอยู่แล้ว (ข้อ 2 และข้อ 10.2) พอเลขขึ้น ห้องจะรู้เองในงานถัดไป

### 11.1 ฝั่งคนแก้นโยบาย (คุณบ๊อบบี้สั่ง AI ห้องใดก็ได้ว่า "อัปเดตนโยบาย: <เรื่อง>")
1. แก้เนื้อหาในเอกสารนี้ เพิ่มเลขฉบับทีละ 1 และเพิ่มแถวในตารางข้อ 9 ให้มีทั้ง "เปลี่ยนอะไร" และ "**ทุกห้องต้องทำ:** ..." ให้ชัดว่าห้องต้องปรับอะไร
2. update Supabase (`content` และ `version = version + 1`) แล้วลงครบทุกที่ตามกฎเหล็กข้อ 1 และเทียบ md5
3. ลงแถวประกาศใน ops_logbook: category `data_system` · title `ประกาศนโยบายกลางฉบับ <N>` · result = สรุปสิ่งที่เปลี่ยนและสิ่งที่ทุกห้องต้องทำ · tags `policy_update`, `policy:v<N>`, `room:<ห้องที่แก้>` · owner `คุณบ๊อบบี้`
4. ถ้าเป็นเรื่องด่วนที่ต้องรู้ก่อนงานถัดไป ให้คุณบ๊อบบี้แจ้งทีมทาง LINE เพิ่มอีกทาง

### 11.2 ฝั่งทุกห้อง (ทำก่อนเริ่มงานทุกครั้ง)
1. เช็กเลขฉบับ: `select version from public.runbooks where slug = 'kumtsu-master-policy';`
2. ถ้าเท่ากับที่จำไว้ ทำงานต่อได้เลย
3. ถ้ามากกว่า ให้อ่านเอกสารใหม่ทั้งฉบับ ดูแถวในข้อ 9 ที่ใหม่กว่าฉบับที่จำไว้ แล้วทำตาม "ทุกห้องต้องทำ" ให้ครบ (ปรับความจำ สกิล runbook ของห้อง ครบทุกที่ตามกฎเหล็กข้อ 1)
4. บอกผู้ใช้ห้องสั้น ๆ 1–2 บรรทัดก่อนเริ่มงาน เช่น "นโยบายกลางเปลี่ยนเป็นฉบับ 3: ต้องใส่ลิงก์ผลงานทุกครั้ง" พนักงานจะได้รู้ไปพร้อมกัน
5. ลงแถวรับทราบใน ops_logbook: category `data_system` · title `รับทราบนโยบายกลางฉบับ <N>` · steps = สิ่งที่ห้องปรับ · status `done` · tags `policy_ack`, `policy:v<N>`, `room:<ชื่อห้อง>`, `by:claude` · created_by = ผู้ใช้ห้อง
6. จำเลขฉบับใหม่ไว้ในความจำของห้อง

### 11.3 คุณบ๊อบบี้ดูว่าห้องไหนรับทราบแล้ว
```sql
-- เปลี่ยน 'policy:v2' เป็นฉบับที่ต้องการ
with rooms as (
  select distinct substr(t,6) room from public.ops_logbook, unnest(tags) t
   where t like 'room:%' and log_date >= current_date - 30),
acks as (
  select distinct substr(t,6) room, min(log_date) ack_date from public.ops_logbook, unnest(tags) t
   where 'policy:v2' = any(tags) and 'policy_ack' = any(tags) and t like 'room:%' group by 1)
select r.room as "ห้อง", coalesce(a.ack_date::text, 'ยังไม่รับทราบ') as "รับทราบเมื่อ"
  from rooms r left join acks a using (room) order by a.ack_date nulls first;
```
ห้องที่ยังไม่รับทราบเกิน 3 วัน จะขึ้นในสรุปรายสัปดาห์วันจันทร์ด้วย
